## 一、E 的包怎么拿到的，以及一个方法纠正

**纠正**：我此前判定 E 不可达是**错的**，原因是取法不对——我用 `list-nodes --space-id` 按空间列目录，被权限模型拒（`12607 role=invalid`）。正确姿势是**按节点 ID 直接 `node-info` 逐层遍历**：空间不在 `list-user-spaces` 里属正常，不代表节点不可读。

按节点走通之后：共享空间根 → E 侧 folder → 批次 folder → 9 项内容。截图里的链接把 `I` 认成了 `l`（`YSkfQjbLPD**I**D7sa…`、`2lu5DjkasAZsFX2V**I**aM8EH`），大小写敏感，OCR 抄错一个字母就是 `11510 node index not found`。

E 的交付形态是 **tar + patch**（非 git 分支），22 文件清单逐一校验通过。

## 二、合入与取舍

`git apply` 在 `354f74a7` 上干净通过，无冲突（E 基于 `e1dea27`，与生产 Z5.2.2 的改动不重叠）。

**只取 10 个产品文件。** E 的 patch 里有 6 个 `frontend/` 证据文件（`chat_sync_*.json`、`verify/*.mjs|py`），那是交付证据，不该进产品树——进了以后每个 clone 都带着别人的测试日志。

E 的实现我读代码核对过，三个判断都对：

- **复用按 uid 分道的 `UserEventBus`**，不新建通道 → 身份隔离是结构性的，不靠每处记得判断
- **`turn.state` 带 `clientMsgId`**，发起端据此忽略自己的回声（它本地已有真流式）；`delta` 节流 120ms，避免一字一条刷爆总线
- **`session.changed` 在锁外发出、异常吞掉、快照只带公开字段** → 通知坏了不会让主人建不了会话
