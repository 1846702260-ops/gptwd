## 三、M1 真实学习阻断修复

### 3.1 复现（先复现、后修，未未经核查重复修改）

在 D 最新候选 `cb4c30a3` 上，用最小装配驱动真实代码路径：

```
=== A-1 注入检测作用对象 ===
原始 HTML  verdict.suspicious = true   hits = ["<script src=\"/static/app.js\">"]
提取正文  verdict.suspicious = false  hits = []
=== A-1 端到端（网关返回含 script 的正常网页）===
tick 结果 state = rejected  lastError = untrusted_directive

=== A-2 语义等价判定 ===
逐字一致   -> candidate
去句号    -> uncertain  unsupported_or_paraphrased
主动改被动  -> uncertain
语序调整   -> uncertain
中英混述   -> uncertain
```

**A-1 根因链（三跳，只修一处不够）**：
1. `research.webRead` 对**原始 HTML** 调 `detectInjection`，命中 `<script src=…>` → `injection.suspicious = true`
2. `web_read` 工具据此在返回正文末尾追加 `[注意] 页面含可疑指令性文本`
3. EvoCore 见 `[注意]` 即 `fail('untrusted_directive')`

**A-2 根因**：`statements.includes(claim)`（整句逐字相等），叠加"恰好两个来源 + 两源不同站点 + 两源非同一稿件"三条，互锁。

### 3.2 A-1 修复

分三层判定，写在 `research.injectionOfPage`：

| 层 | 内容 | 处理 |
| --- | --- | --- |
| 网页结构 | 有无 `script`/`iframe`/隐藏容器 | **只记录**，不作拒绝依据 |
| 可执行内容 | `<script>` 内联代码 | 仍判指令性文本 |
| 可读正文 | 提取后进入上下文的部分 | **严格判** |

配套改动：
- 指令模式与结构模式拆开：新增 `detectDirective`（6 条指令模式），`detectInjection` 保留原 7 条向后兼容。这样代码文档正文里的 `<script>` 示例、内联脚本里的 `document.write('<script…>')` 不再误判。
- 隐藏区域：不再"整页有 `display:none` 就可疑"，改为"隐藏区域含指令性文本"或"藏大段文本且进入正文"才算可疑。现代页面的下拉/模态/无障碍文本不再误报。
- `webRead`：判定延后到正文定稿之后；headless 渲染成功时把渲染 DOM 的脚本体并入判定（深度防御）。
- EvoCore：先取可读正文再判；**保留**工具层 `[注意]` 标记作为独立一层（不轻信单一环节）——因为工具层已修好误标，这层不再误伤，但真注入仍拦得住。

**安全性未降低**：注入要生效必须进入模型上下文，进上下文的是正文；正文里的 `ignore previous instructions` 仍命中并拒绝。现有 D 的安全属性测试（`gateway injection warning blocks matching text and no memory is promoted`）保持通过。

### 3.4 A-2 修复

新判定用**确定性规则**（G 明令不得仅凭相似度/域名数/模型自评）：

| 判据 | 内容 |
| --- | --- |
| ① 词项全覆盖 | claim 的全部实词须出现在候选句（子集关系） |
| ② 数字一致 | claim 的每个数字须出现在该句；数字不同 → `conflict/numeric_mismatch` |
| ③ 极性一致 | 否定相反 → `conflict/negation_mismatch` |
| ④ 规范化包含 | 去标点/空白/连字符后 claim 整体出现在句中 |

①②③ 全满足 → `candidate / semantic_equivalence`；只覆盖 ≥0.75 → `uncertain / low_confidence_overlap`；否则 `uncertain / unsupported_or_paraphrased`。

**只取得候选资格**：无论逐字还是等价，都必须主人 `approve` 才写 memv2；`autoApply` 默认关闭且不因文本一致而自动晋升。

**句末标点缺陷消除**：claim 不带句号也判 `semantic_equivalence`（原判据因切分把标点留前段而永远匹配不上）。

**跨语言不通过**：`Node.js 22 是当前 LTS 版本` 仍判 `uncertain`。这是能力边界，如实登记 —— 跨语言等价需翻译或蕴含模型，不在本轮授权内。

### 5.3 发现并修复的接口断裂

`finishCommit` 晋升后执行 `delete entry.claim / evidence / urls`，注释理由是"memv2 是唯一真源，状态文件不重复存"。原则正确，但副作用是 `GET /goals/:id` 对已晋升目标只返回 `id/state/atomId` —— 前端详情页刷新后看不到"她在学什么"，也看不到证据。

修法：**状态文件仍不重复存**（保留真源唯一），`inspect` 对 promoted 目标从 memv2 原子回填 `claim` 与 `evidence`（只读投影，不落盘）。取不到原子照旧降级 `erased`，原子不活跃降级 `inactive`。

同步更新 D 的一条过期断言（原断言把"不重复存"这件事断言在对外接口上）。

### 5.4 技能链路的真实边界（未扩大范围）

- 技能候选**可以生成**（复用 `SkillLab.createCandidate`，source=`evocore:<goalId>`，初始 DRAFT）
- 候选**无法枚举**：SkillLab 没有列表路由，`/api/ws/skills` 是另一套"按运行提炼"的技能
- **测试与提审无 HTTP 入口**：DRAFT→TESTING→VALIDATED→提审 的状态机存在，但没有对外路由
- E 的选择是**不放假按钮**，页面上如实写出边界 —— 这是正确处理，不记为缺陷

完整技能生命周期需要新增路由与状态机对外接口，属架构变更，按 G 要求**明确登记不扩大本轮范围**。
