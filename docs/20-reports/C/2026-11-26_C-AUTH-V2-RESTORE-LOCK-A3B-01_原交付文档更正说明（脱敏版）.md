## 三、更正后的事实

**"共同门禁覆盖旧 Cookie"这一表述不成立。** 实际上：

上轮的门禁只挂在 `AuthService.#requireOwner`，覆盖的是**认证操作**（密码登录、TOTP 验证、恢复码、Passkey 登记/验证、重新认证、主人会话签发）。

而网页侧的身份判定走的是**另一套** `WebSessions.resolveEx()`。凡是直接用 `resolveEx` 的结果判 `kind === 'owner'` 的入口，都**完全绕过**了上轮门禁。

实测（`test/auth-v2/c-a3b-defect-evidence.mjs` A 段，真实启动 + 真实整目录回滚）：

| 入口 | 上轮（`d311e152`）实际结果 | 应有结果 |
|---|---|---|
| `GET /api/web/auth/status` | **`state=full`**（且同时 `locked=true`） | 非 full |
| `GET /api/web/session-info` | **200，kind=owner** | 401 |
| `GET /api/web/sessions`（工作区会话列表） | **200** | 401 |
| `GET /api/web/devices` | **200** | 401 |
| `POST /api/ws/projects`（工具/工作区写入） | **200** | 401 |
| `GET /api/web/persona/status`（人格） | **200** | 401 |

即：上轮声称的"旧 Cookie 全部受保护"**未成立** —— 锁定期间旧 Cookie 仍能拿到主人全权，且 `status` 同时返回 `full` 与 `locked=true`。

## 四、根因（为什么上轮会漏）

不是某个 `if` 写错，而是**闸门挂错了层**：

- 上轮把恢复锁定门禁挂在**业务方法**（`#requireOwner`）上；
- 网页身份判定走**身份解析层**（`WebSessions.resolveEx`）；
- 两层之间没有打通。

逐路由补 `if` 必然继续漏 —— 本轮实测就漏了至少五个入口。

## 五、本轮更正与修复

本轮（候选 `adfc9ed`，分支 `cand/auth-v2-restore-lock-a3b-01`）把闸门下沉到 `WebSessions.resolveEx()` —— 全系统**唯一**的"令牌 → 身份"入口：

- 锁定期间主人令牌解析不出身份（返回 `null`），下游一律按"无身份"处理（401 / anonymous）；
- 覆盖网页 HTTP、认证 status、会话列表、设备、工作区、工具/WS、人格等**全部**主人专属入口，不再逐路由遗漏；
- `status` 在锁定期间只能落 `anonymous`，不可能同时 `full`；
- 锁的是**主人**，不是整站（普通用户与服务身份不受影响）。

修复后同一枚旧 Cookie 的实测结果（六入口全 401 + status 非 full）见 `03-完整性验证报告.md` 第 2 节 B 段与 `06-测试证据与变更说明.md` 第四节。
