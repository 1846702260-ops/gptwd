本轮只解决 C 验收提出的 R-08′：归档 manifest 采用「读 → version+1 → tmp+rename」，rename 只保证单次写原子，不构成 CAS，也无文件锁。两个进程同时读到 version=N、各自写 N+1，后写覆盖先写；先写者的段成为孤儿，原文从恢复链消失。用真实独立进程复现修复前源码：6 进程 × 20 轮 × 5 条，20/20 轮失败，600 条确认记录丢失 245 条，每轮均有孤儿段，与 C 的机制判定一致。

修复做法是最小一致性，不重建存储引擎：为同一 `(userId, sessionId, scope)` 的归档事务加一把跨进程文件锁。锁用 `open(..., 'wx')` 在本地 POSIX 盘上原子创建，覆盖「读 manifest → 写段 → 写 manifest」完整读改写，而不是只锁 rename；取得锁后重新读取 manifest 再计算差异与序号，并发新增不被覆盖。锁有 5 秒有界等待，崩溃残留锁仅在超过 30 秒且持有 pid 不存活时接管，持有者存活则绝不抢占；释放只删自己 token 的锁。段与 manifest 改为临时文件 → fsync → rename → 目录 fsync；段先落盘、manifest 再提交，任何失败返回 `ok:false`，调用方不移出热窗口原文。重建索引纳入同一把锁。R-07′ 同步收紧：`pruneArchives` 默认只盘点、不物理删除唯一原文，必须 `authorized && hardDelete && !dryRun` 三条件显式授权才删；用户明确删除/隐私擦除仍走 `redact`。
