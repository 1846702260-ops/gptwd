# GitHub 迁移协同核查（C-GITHUB-UNIFIED-MIGRATION-01）

**结论**：两个私有仓库**访问成功且已有源码**；生产侧存在两层"看似不可达"的假象（死代理、HTTP/2 挂起）。**未改任何远端地址、未加 remote、未配 key。**

## 一、判定表

| 检查 | 结果 | 判据 |
|---|---|---|
| 在沙箱（同 token） | 可访问，私有 | `api=200`、`private=true` |
| 在生产（默认环境） | **失败** | 全部 `Failed to connect to 127.0.0.1 port 2080` |
| 在生产（绕过代理） | **成功** | `api.github.com` 200；`info/refs` 200；TLS 0.21 s |
| `git ls-remote` 默认 | **60 s 超时**（2 次） | 退出码 124 |
| `git ls-remote` + `http.version=HTTP/1.1` | **成功** | 返回完整 refs |
| SSH 22 | 连通 | `Permission denied (publickey)`（无 deploy key） |
| 仓库是否为空 | **否** | 见第二节 |

## 二、仓库实际内容

| 仓库 | 分支/标签（部分） |
|---|---|
| `zhiyao-agi` | 标签 `Z1.4.7`…`Z1.4.7.4`；分支 `baseline/evocore-v1.0-freeze-01`、`c-mindcore-baseline-sync-02`(`6a5efbde`)、`c-mindcore-integration-01`(`39bd712f`)、`c-final-integration`、`c-release-closeout-02` 等；默认分支 `release/z5.2.2` |

> 任务书预设"仓库为空时需区分访问成功与尚无源码"。**本轮不属于该情形**：内容已在，应按"已迁移、待切换引用"推进，不能当作等待首次推送。

## 三、根因

### 3.1 死代理（第一层假象）

```
https_proxy=http://<DEAD_PROXY>     # 无监听
NO_PROXY=localhost,127.0.0.1,*.cn,baidu.com,qq.com,taobao.com
```

任何 `curl`/`git` 都先连 2080 → 立即失败。`ops/deploy-linux.sh` 已内置绕行（仅当代理恰为该死端口时 `env -u`），所以**自动部署能正常 fetch**，而人工在 shell 里测会全部失败——这正是"Gitee 直连令牌失效/出网受限"的由来。

### 3.2 HTTP/2 挂起（第二层假象）

绕开代理后：`info/refs` 200、`curl https://github.com` 200，但 `git ls-remote` 默认协议 60 s 无响应；加 `-c http.version=HTTP/1.1` 立刻成功。判定为 **HTTP/2 在该链路（MTU/中间设备）不可用**，不是认证或仓库问题。

### 3.3 认证

`api.github.com` 带 token 200；`git` 带 `x-access-token:<PAT>` 在 HTTP/1.1 下成功；SSH 22 通但生产无 key。

## 四、迁移影响面（只读盘点）

| 位置 | 现值 | 迁移要改 |
|---|---|---|
| `<REPO>/.git/config` | `origin=https://gitee.com/<GITEE_REPO>.git` | 是（远端 URL） |
| `ops/deploy-linux.sh:24` | `BRANCH="release/z5.2.2"` | 是（分支名随发布走） |
| `ops/deploy-linux.sh:113-126` | 死代理绕行 + `git fetch origin $BRANCH` | 否（逻辑可复用） |
| `ops/check-env.sh:57` | 提示 `git clone https://gitee.com/...` | 是（文案） |
| `ops/zhiyao-companion.service.template:14` | `Documentation=https://gitee.com/...` | 是（文案） |
| `/etc/cron.d/zhiyao-switch` | 每分钟 `ops/switch/ensure.sh` | 否 |
| 每日备份 | `/etc/zyagi/backup.env`（NAS）、`ops/backup-daily.sh`、`<BACKUP_DIR>/*.tar.gz` | 否（与仓库无关） |
| 凭据 | `<GIT_CRED_FILE>`（文档记载，600） | 是（换 GitHub 凭据） |

## 五、建议的切换前置（未执行）

1. `git config --global http.version HTTP/1.1`（或修好 2080 代理，二选一；前者影响面小）。
2. 在 GitHub 侧生成 **fine-grained PAT（只读 + contents:write）或 deploy key**，落在 `<GIT_CRED_FILE>`，权限 600。
3. `git remote add github ...` 与 `git remote -v` 双远端并行**观察一个发布周期**，先只读 fetch，不切部署。
4. 确认 `git ls-remote github release/z5.2.2` 与本地 HEAD 一致后，再把 `deploy-linux.sh` 的 `origin` 指向 GitHub。
5. 保留 Gitee 远端 ≥ 1 个发布周期作为退路。

**风险提示**：HTTP/2 若在部署脚本里没显式降到 1.1，cron 每分钟的 fetch 会长时间挂起并堆积进程；切换前应先在脚本里显式加 `-c http.version=HTTP/1.1`。
