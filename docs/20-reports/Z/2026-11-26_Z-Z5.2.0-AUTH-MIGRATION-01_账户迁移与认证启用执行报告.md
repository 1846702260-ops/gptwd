## 三、迁移阻断与解除（关键发现）

**根因**：`data/web/account.json` 是**上一代遗留物**（`user=zhiyao`，而当前 `config.web.account.user=owner`）。生产登录走 `verifyAccount` 的 `passwordManaged` 分支（env 明文比对），**account.json 的 scrypt 哈希根本不参与认证**。标准 `auth-init` → `migrateLegacyAccount` → `verifyLegacyAccountPassword` 必然被拒（`bad_credentials`）。

**解除方式**：用官方 `zyagi-admin reset-owner-password --no-revoke --no-reload` 将 account.json 的哈希**重新对齐到权威凭据源**（同一口令、新盐），主人 171 条会话与非目标 179 条身份**均未触碰**，工作区干净。随后 `auth-init` 走标准 `migrateLegacyAccount` 路径成功。

**迁移结果**：`accountId=acct_18c472a081519e75`，`ownerSource=config`，`emailVerified=false`（无 SMTP，邮箱仅作登录名），`generation=1`，`auth.json` 无明文。

## 六、生产故障与修复（本轮发现并已修复）

### 6.1 【严重】撤销墓碑口径不一致 → 主人全站被拒（deny-all）

**现象**：迁移验证过程中出现「登录 200 但会话立即 401」，审计报 `identity.tombstone_tampered_deny_all` / `TOMBSTONE_LINE_COUNT_MISMATCH`。

**根因**（`packages/companion/src/lib/revocation-tombstone.mjs`）：
- `writeSeal()` 记录 `lines` = **非空行数**（含重复行）
- `loadTombstone()` 校验时用 `result.map.size`（**Map 去重后**）+ bad
- 同一令牌被撤销 ≥2 次时，两者必然不等 → 误判 `tampered` → **fail-closed 拒绝全部主人身份**

生产实证：墓碑 186 行中 hash `125171d7…` 被写 3 次（`password_change` + 2×`session_rotate`），`map.size=184` vs `seal.lines=186` → 不等。

**触发条件普遍**：改密 + 会话轮换 + "退出其他设备" 都会撤销同一令牌，**真实生产必然触发全站拒绝**。

**修复**（数据层，已生效）：同 hash 只留最早一条 → 184 行，`seal.lines=184` → `tampered=false`、`reasons=[]`、`mapSize=184`。备份 `/root/backups/TOMBSTONE-FIX-PRE-01-20261126T084247`。

**根本修复（待 C 修）**：`writeSeal()` 应记录**去重后**计数，或 `appendTombstone()` 追加前去重；`loadTombstone()` 校验需与写入口径一致。当前两端口径已因数据去重而一致，但**代码缺陷仍在**，下次重复撤销会再次触发。

### 6.2 【中】CLI `resolveDataDir()` 路径猜测错误 → 回退检测假阳性

**现象**：按 `docs/auth-v2/06-迁移与回滚.md` 执行 `auth-verify-restore`，在锚点被人为调高（模拟旧备份覆盖）时仍报「✓ 未检测到回退」。

**根因**（`packages/companion/bin/zyagi-admin.js`）：`resolveDataDir()` 用 `cwd + packages/companion/data` 猜测。从 `packages/companion/` 内执行时猜到 `packages/companion/packages/companion/data`（不存在）→ `store.exists()` 为 false → `restoreLocked` 直接返回 false → **回退检测被静默跳过**。影响 11 个 CLI 命令。服务侧 `loadConfig` 的 `rel()` 以 config 目录为基准，**口径本不一致**。

**已修复（文档面）**：`06-迁移与回滚.md` 8 处 CLI 示例全部补 `--config ./config.json --data-dir ./data`，并加警示段落。实测：修复后写法正确检出 `state=3 < anchor=99`，旧写法仍假阳性。

**根本修复（待 C 修）**：`resolveDataDir()` 应优先读 config 的 `dataDir`（相对 config 目录），与 `rel()` 对齐。

### 6.3 【低】`reset-owner-password` 缺 `--data-dir` 时写入重复路径

从 `packages/companion` 内执行会写到 `packages/companion/packages/companion/data/web/account.json`。本轮已发现并**立即清理**该误写产物，真实 `account.json` 与源码均未被污染。
