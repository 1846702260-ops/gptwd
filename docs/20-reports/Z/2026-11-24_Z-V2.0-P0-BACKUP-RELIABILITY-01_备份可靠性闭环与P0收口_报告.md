| 用途 | 旧代码（错） | 实测真契约 | 造成的误报 |
|---|---|---|---|
| 存在性判定 | `file stat {path}` | `file info {path}`，读 `data.size` | `E_PARAM: file 不支持 action stat` → 恒判"远端不存在" |
| 列目录 | 读 `data.files[]` | `file list {path}` 读 `data.list[]` | 计数恒为 0 |
| 下载 | `{path, dest}` | `{path, local_path}`（需 `--yes`） | `缺少参数 local_path` |
| 建目录 | `file mkdir {path}` | `{parent, name}`，单层 | `输入含未声明字段` |
| 上传 | `{local_path, dest_path}` | 同左，同名 `E_EXISTS` | 同名覆盖判定缺失 |

```bash
_zs_ok()     { printf '%s' "$1" | grep -Eq '"ok"[[:space:]]*:[[:space:]]*true'; }
_zs_exists() { printf '%s' "$1" | grep -q 'E_EXISTS'; }
```

未使用"忽略退出码""强设 `ok=true`""关闭告警"等任何掩盖手段。

合成样本交叉验证：1 / 4 / 8 MiB 通过；9 / 10 / 12 / 16 / 24 / 32 MiB 全部被拒 → 阈值 **8 MiB（8,388,608 字节）**，与文件内容无关，只与"是否触发多块下载"有关。

**为什么不能"修"这条约束**：远端元数据 `etag=None`、`file_hash=''`，`download` 不接受 `etag / version / offset` 参数，因此无法提供"强绑定文件版本"的前置条件；CLI 也未暴露服务端强校验和。按任务书 4.1 末段，此处**记录证据并转 4.2**，未关闭、未绕过 TLS/版本绑定/完整性检查。

另核实 `file read` 不能替代：它支持 `offset/next_offset/truncated`，但 `encoding=text`，对 200,000 字节二进制分段读取后重组仅得 189,578 字节且哈希不符 → 对归档有损，不可用于回读。

### 3.2 方案 B（分片）设计与实现

- 输入：已生成并通过校验的完整归档，**不改变归档内容、加密、清单与恢复语义**，只在传输层加分片；
- 片大小 4 MiB（对 8 MiB 上限留 50% 余量，可用 `NAS_SHARD_PART` 覆盖）；
- 命名：`<远端唯一快照目录>/part-0000.bin …`，序号零填充、按 manifest `parts` 顺序重组；快照目录用时间戳 ID，**每次唯一，不覆盖上一份成功备份**；
- 清单 `manifest.json`：格式版本 `shard/v1`、原包长度与 SHA-256、每片序号/字节数/SHA-256、总片数；清单本身不承载秘密；
- 完成标记：**全部片上传并逐片校验通过**才写 manifest；未完成不发布完成标记；
- 读端：下载 manifest → 逐片下载 → 逐片 SHA-256 → 按序重组 → 整包长度 + 整包 SHA-256 双重校验；任一不符即失败，**不输出半包**。
