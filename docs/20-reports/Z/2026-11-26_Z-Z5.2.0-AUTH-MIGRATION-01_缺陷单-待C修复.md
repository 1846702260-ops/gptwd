## D-01【严重】撤销墓碑 seal 行数口径不一致 → 主人全站被拒（deny-all）

### 位置

`packages/companion/src/lib/revocation-tombstone.mjs`

### 问题

同一令牌哈希被写入墓碑 ≥2 次时，`loadTombstone()` 误判 `tampered=true`，`resolveEx()` 进入 fail-closed **拒绝全部主人身份**（网页、工作区、工具、WS 全部 401）。

### 根因（两端口径不一致）

| 位置 | 计数口径 |
| --- | --- |
| `writeSeal()` | `lines = buf.toString('utf8').split('\n').filter(l => l.trim()).length` → **非空行数（含重复）** |
| `loadTombstone()` | `result.lines = result.map.size`（**Map 按 hash 去重后**）；校验 `Number(seal?.lines) !== result.map.size + bad` → **去重后计数** |

`appendTombstone()` 用 `appendFileSync` 追加，**不去重**（`skipped` 只统计 hash 格式非法的条目）。

因此：`seal.lines` = 186（含 1 个 hash 写 3 次）而 `map.size + bad` = 184 → 判定 `TOMBSTONE_LINE_COUNT_MISMATCH`。

### 生产实证

```
墓碑 186 行；hash 125171d72e1c0577fc300bb7c6938b4c9681a31926ad7d37119f976a6d138e7a 出现 3 次
  行3   reason=password_change  at=1795652798860
  行181 reason=session_rotate   at=1795652988166
  行184 reason=session_rotate   at=1795653130057
loadTombstone → { tampered:true, lines:184, mapSize:184, reasons:["TOMBSTONE_LINE_COUNT_MISMATCH"] }
审计 → identity.tombstone_tampered_deny_all
现象 → 登录 200 但会话立即 401；主人全站不可用
```

### 触发条件（生产必然发生）

以下动作都会撤销同一令牌，从而写入重复 hash：
- 改密（`password_change`）
- 会话轮换（登录后旧令牌立即失效，`session_rotate`）
- "退出其他设备"（`logout-all`）
- 同一令牌被多次 `revokeIdentity`

### 建议修复（择一或兼施）

1. **写入口径对齐**：`writeSeal()` 记录**去重后**的有效 hash 计数（与 `loadTombstone` 一致）；
2. **更彻底**：`appendTombstone()` 追加前读取现有墓碑，跳过已存在的 hash（墓碑语义本就是"这个令牌已被撤销"，重复行不增信息量；但若需保留审计轨迹，可另存审计日志）；
3. **兼容旧 seal**：`loadTombstone()` 在校验时同时接受"非空行数"与"去重后计数"两种口径，避免历史文件被判篡改。

### 修复要求

- 必须保留 tamper 检测能力（sha256 不符、seal 缺失、坏行仍须 fail-closed）
- 需补测试：同一 hash 撤销 2 次以上 → `tampered=false`
- 需回归：`resolveEx` 对墓碑中令牌的拒绝行为不变

### 本轮已做的缓解（不改代码）

- 生产墓碑已去重：同 hash 只留最早一条 → 186 → **184 行**
- seal 重算：`lines=184`，`sha256` 与文件一致
- 复验：`loadTombstone → { tampered:false, lines:184, mapSize:184, reasons:[] }`
- 备份：`/root/backups/TOMBSTONE-FIX-PRE-01-20261126T084247`

## D-02【中】CLI `resolveDataDir()` 路径猜测错误 → 回退检测假阳性

### 位置

`packages/companion/bin/zyagi-admin.js` → `resolveDataDir()`

### 问题

不带 `--data-dir` 执行时，CLI 猜到的数据目录与服务实际使用的不一致，导致 `auth-verify-restore` **读不到 `auth.json`，回退检测被静默跳过**并误报「✓ 未检测到回退」。

### 根因

```js
function resolveDataDir() {
  if (args['data-dir']) return path.resolve(String(args['data-dir']));
  if (process.env.ZY_DATA_DIR) return path.resolve(process.env.ZY_DATA_DIR);
  const guess = path.resolve(process.cwd(), 'packages', 'companion', 'data');  // ← 基于 cwd 猜测
  return guess;
}
```

服务侧 `loadConfig` 的 `rel()` 以 **config 文件所在目录**为基准解析 `dataDir`，CLI 却以 **cwd** 猜测，两者口径本就不一致。

在 `packages/companion/` 内执行时：cwd 猜测 → `/root/zyagi/packages/companion/packages/companion/data`（重复路径，不存在）。

### 生产实证

```
锚点改为 99（模拟旧备份覆盖），auth.json 代际 3：
  不带 --data-dir → ✓ 未检测到回滚，也未处于恢复锁定   ← 假阳性
  带 --data-dir    → ⚠ 检测到认证状态代际回退：state=3 < anchor=99   ← 正确
```

因 `store.exists()` 为 false → `restoreLocked` 直接返回 false。

### 影响面

`resolveDataDir()` 被 **11 处** 调用：
`reset-owner-password`、`service-issue`、`service-list`、`service-revoke`、`audit-tail`、`status`、`migrate-legacy-owner`、`security-posture`、`auth-init`、`auth-status`、`auth-issue-recovery`、`auth-recover`、`auth-verify-restore`。

**最危险的是 `auth-verify-restore`**：运维照文档执行会得到虚假的安全确认。

### 建议修复

`resolveDataDir()` 优先读 config 的 `dataDir`（相对 **config 目录**解析），与服务侧 `rel()` 对齐；仅当 config 不可读时才回退到 cwd 猜测，并给出明确告警。

### 本轮已做的缓解（不改代码）

- `docs/auth-v2/06-迁移与回滚.md` 中 **8 处** CLI 示例全部补 `--config ./config.json --data-dir ./data`
- 5.3 节新增警示段落，说明漏写 `--data-dir` 会导致回退检测被静默跳过
- 实测：修复后写法正确检出 `state=3 < anchor=99`
