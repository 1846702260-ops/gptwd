## 五、缺陷 B-5：修订脚本 L02 判定器的调用点不一致

### 5.1 现象

用 **C 原脚本**（`s2-live-models-fix01.mjs`，逐字节未改）跑真实调用，两模型 L02 均 `FAIL reason=no_new_value`，但回答内容完全正确：

- hy4flash：`你现在住在杭州——上个月从成都搬过去的。`
- DeepSeek-V4.1-Flash：`杭州。你上个月刚从成都搬过去，成都那条已经作废了。`

### 5.2 根因（最小复现）

脚本第 340 行调用 `sc.judge({ text: askRes.text })` 传的是**对象**；而 `judgeL02(text)` 的形参是**字符串**，内部 `String(text || '')` 得到 `[object Object]` → 既无"杭州"也无"成都" → 必然落到 `no_new_value`。

```
judgeL02({text:'你现在住在杭州——…'}) = {"ok":false,"why":"no_new_value"}
judgeL02('你现在住在杭州——…')        = {"ok":true,"why":"new_current_old_historical"}
```

C 报告里的正负对照表是以**字符串**直接调用的，因此该表的 5/5 成立、而脚本跑起来必然全红——这是"报告口径与运行口径不一致"，属**测试工具缺陷**，不涉及产品代码，也不是模型能力问题。离线模式下 `ok=null` 不触发判定，故 C 侧的 dry-run 无法暴露它。

### 5.3 Z 侧处理（不掩盖、不改规则）

1. **保留**C 原脚本的 6 次 FAIL 结果作为证据（`evidence/Z-r1.json`、`Z-dbg-L02.json`）；
2. 另建 `s2-live-g5z-fixcall.mjs`，只改**调用点**一行：`sc.judge === judgeL02 ? judgeL02(askRes.text) : sc.judge({text})`；
3. `g5-judges.mjs` **逐字节未改**（`bd53865a…`），判定规则、阈值、正则全部沿用；
4. 两轮正式结果均在该"仅修调用点"的副本上产生，并在报告中同时给出原脚本结果。

建议 C 后续最小修复：把 `judgeL02` 改成收对象 `({text})`，或统一所有判定器签名——两者任选其一，规则不动。
