## 结论摘要
完成 DSH 与外部插件生态隔离适配研究。核心判断：**真实第三方插件的静态分析能力可经独立 adapter 复用，不依赖完整 DSH 聊天框架，已用真实代码走通最小链**；但第三方运行时能力不可盲目执行，完整链因无凭据 BLOCKED。维持"不用 DSH 作主架构"，复用方向以标准 Skill/MCP（E1）为主。

## 一手研究（官方一手）
- DSH 官方仓库 MIT 许可、开发者预览；当前 0.2.3-alpha.2，短期内两次 alpha、破坏性变更常态、Node 底线抬升——不适合作为主线运行时。
- SDK 为按行分帧 JSON-RPC over stdio，具名 profile + 有序 patch；Python SDK 强制显式隔离 home、提供三档权限预设与可逐项拒绝的审批协议、sandbox 多后端。
- 选型：低风险真实插件 dsh-plugin-toolkit（Apache-2.0）做 PoC；Agent Memory 类插件（含 OAuth 与记忆写权）仅作源码研究、绝不执行、仅借鉴机制。对比 OpenClaw（bundle-style 插件、单一记忆槽）后确认：借鉴插件分层与单记忆约束，不引入框架。

## 最小 PoC（隔离环境）
在隔离目录只读 clone 真实插件源码（固定 commit、零依赖安装、无安装钩子），审查确认其静态分析纯函数链仅依赖标准库、不 import 被检查代码。自写 adapter 调用真实门控函数走通"发现→加载→调用→结果→卸载"：合规合成插件通过、违规插件被多项门控拒绝、未授权方法被拒、卸载后能力不可再调用；真实插件源码自检通过。全程无网络、无真实账号/数据、未调用真实模型、未消耗额度，全部标注 mock。完整 DSH SDK 真实模型链 BLOCKED（无运行时、无授权额度），已给最小必要条件，未获取任何秘密。

## 对比与裁决材料
四方案：A 独立 SDK 子进程（仅研究通道）、B 转标准 Skill/MCP（主推荐）、C 源码抽取融合（高成本、第二真源隐患）、D 放弃 DSH 主线保留生态观察（当前处置）。兼容性矩阵：静态分析工具=薄适配可行、SDK 协议=薄适配/独立、记忆类插件引入=不可行（第二长期记忆源一票否决）、其他框架思想=机制借鉴、DSH 主架构=不可行。接口映射：门控结果→登记前校验、权限预设→风险分级、审批→现有审批网关、记忆/人格/外部高风险→一律禁止或默认拒绝。E0 历史安全线索移交 E/C 复现，R 不重复实现。

## 建议与待裁决
E1 可吸收项：将第三方插件静态分析纳入登记前校验（复用为主，不改核心）。E2 最小试点（R 不自启）：仅在裁决通过、授权模型凭据与额度、隔离 home、专用分支下，验证真实 SDK 握手 + 一个只读合成工具；出现生产连接、凭据越界、第二记忆源或未审查代码执行即熔断。研究结果交 ChatGPT 裁决，R 不改正式基线、不自派任务。
