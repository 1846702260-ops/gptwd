## 一、这次修的是什么

C 报告指出的三个缺口，本质相同：**逻辑早就写好了，只是没人调用**。所以本批不做架构重构，只做"接线 + 补出口 + 堵住接线后暴露的真 bug"。

1. **M1 受保护事实有进无出**：`correctionPending` 的入队、确认、拒绝全都在，但全仓零调用方 —— 主人根本看不到队列，也批不了。补了三条真实 HTTP 出口（列出/确认/拒绝）：`fromOwner` 由服务端置真、非主人 403、scope 锁 private、重复确认 409 且只落一条新原子。
2. **M2 摘要投影没接线**：`projectSlots` 无导入方，注入侧还在用整句替换。接线后按 source ID/状态/scope 投影，只注入现行槽位。
3. **M3 双源并行**：`people.json` 的 traits/facts 直接进提示词，绕开 memv2 治理。改成派生层投影（纠正→后继、遗忘/过期/休眠→不注入、跨档→不注入、沿 supersede 链取链尾），并把印象提炼结果同步写 memv2（`inferred`，不自动升级为受保护事实）。

## 二、接线时撞出来的三个真 bug

这些不是推测，是沿真实路径追出来的：

- `memv2.correct` 给**新原子**写了 `invalidatedBy=old.id`，`isInvalidAt` 一律按"本原子被失效"读，于是**每一条纠正后的新事实都被判为已失效**，摘要永远解析不到后继。修法不是删字段（那会丢掉 S3-M1 已验收的"纠正沿革"），而是让判定看状态：active 原子不可能已失效。
- `projectSlots` 只挡 `superseded`，`forgotten/expired/dormant` 照旧当现行注入 —— "用户说忘掉、她还在念"。
- `purge` 是物理删除，派生层查不到原子就按"历史遗留"放行 —— **彻底删除的事实会复活**。墓碑补正文指纹（不存正文），命中即视为已删除。

## 七、兼容性与回滚

本批没有新增依赖、没有改必填字段、没有动磁盘布局：
- `renderPerson(id, { scope })` 第二参数可省略，旧调用形态（QQ 侧、独立脚本、老测试）行为逐字节不变；
- 未装配 memv2 时投影整体不生效，等价于改造前；装配语句只有一行（`memory.attachMemv2`），出问题摘掉即可回滚，不必回滚数据；
- `projectProfile` 是纯函数、只读、不写盘，可用任意原子数组离线复算，便于 C 侧独立核对；
- 治理层读盘异常一律 fail-open 到旧行为 —— 画像不会因为治理层故障而整段清空（宁可少一层筛选，也不能让她突然"不认识主人"）；
- 墓碑新增 `textHash` 为可选字段，旧数据缺失时按"无指纹"退回原逻辑，不做批量改写。
