## 三、执行顺序与授权边界

本任务只授权阶段 A（准备及隔离验证），不自动进入阶段 B（实际生产变更）。主人回复同意本任务不等于批准后续生产操作。

1. **A0：** 核对输入、已通过证据、生产现状以及当前有效授权。
2. **A1：** 对本机免密身份、凭证管理进行最小必要处置设计及隔离验证。
3. **A2：** 整理已验收候选的依赖与发布组合，验证真实恢复和回滚准备。
4. **A3：** 输出最终门禁矩阵、明确的生产操作授权清单、可执行手册和唯一准备候选（如适用）。
5. **B：** 仅在 ChatGPT 审核、主人明确授权具体范围后，另行进入生产执行。此任务到 A3 为止。

任何需要真实生产写入才能证明的事项，先记录为“待授权后验证”。不得以测试环境结果冒充生产实证。已获其他明确授权的正常运维事项不因此被取消，但不得借用旧授权执行本次新增高风险操作。

## 四、必须完成的工作

### M1｜本机免密主人身份风险（A1）

目标：使未经主人授权的访问不能因为来源被判定为本机而获得主人身份或高权限。

1. 在不暴露生产地址、密钥或具体可利用细节的前提下，从现有实现和真实部署拓扑核实免密身份机制、信任来源、调用方、实际依赖、可达性及权限范围。区别操作系统本地运维认证和应用层主人身份授权，不能混为一谈。
2. 优先复用已有认证能力与配置开关，比较关闭默认免密和必要服务身份最小授权两种处置。若确需保留本地服务调用，必须明确独立身份、作用域及授权凭据，不因“本机”自动取得主人身份。
3. 仅在隔离环境实施最小配置或代码修复；涉及通用认证架构重大修改、广泛 API 兼容性调整则暂停该部分并上报总协调，由 C/K 按职责协作，不自行扩大范围。
4. 定向验证：未认证访问不能取得主人身份；普通用户与非主人服务身份不能获得主人高权限；经授权主人及必要合法服务仍可使用；异常或身份不可确认时默认拒绝；已有改密、会话撤销及身份隔离成果不退化。根据实际入口补充必要相邻测试，不做全仓回归。
5. 报告必须明确：候选是否已修复、生产是否仍存在、上线需改变哪些配置或代码、如何安全恢复合法主人访问。不得提出重新开放不安全免密机制作为常规回滚方法。

验收：有可复现的修复前后对照证据；无法完成最小修复时明确原因和所需协作，不能仅凭“只限本机”认定 A 类风险已关闭。

### M2｜明文凭证与副本风险（A2）

目标：避免凭证无必要地保存在可读配置、日志或备份副本中，并为真实泄露处置建立可操作方案。

1. 在既有只读授权范围内核查凭证类别、保存位置类别、使用者、权限、是否进入备份或外部归档、可轮换性及依赖关系。只记录脱敏类别和数量等必要信息，不打印、不复制、不上传真实值，不将凭证当作测试样本。
2. 区分实际外泄证据、存在不必要副本与仅受控本机存储。已有证据显示真实泄露时单独标为紧急授权事项，不等待常规发布流程；不能以尚未发现外泄证明没有泄露。
3. 优先利用当前运行环境已有安全注入和权限机制（例如受控服务凭证或权限受限的配置入口，具体以实际环境可用能力为准），不引入重型密钥平台。隔离测试使用虚构凭证，验证正常启动、缺失或无效凭证时安全失败、日志脱敏、备份排除敏感配置，以及恢复后合法服务如何取得新凭证。
4. 提交最小轮换顺序、依赖服务影响、授权操作边界、撤销旧凭证与验证新凭证的方案。明确历史备份和其他副本的处置策略；保留必要恢复能力与证据，不未经授权删除历史文件、不覆盖远端历史包。
5. 如需要变更生产备份上传行为来临时止血，必须单列理由、影响、替代保护及恢复条件供主人决定。本任务不授权暂停现有 NAS 任务。

验收：隔离验证证明安全注入及失效处理可行，轮换与副本治理计划可执行。生产凭证未实际轮换或风险未实际隔离前，不宣布 A2 已关闭。禁止在公开 GitHub 披露真实凭证、内部坐标或可利用细节。

### M3｜NAS、R3 和 S1 的发布组合（A3 及账户安全落地）

目标：使已验收的补丁能够按可复现的路径进入同一可发布版本，而不回退任何已通过修复。

1. 复用 NAS-A1、R3-03、S1 的现有隔离验收证据，建立候选来源、父链、文件交集、依赖和冲突矩阵；特别检查生产在途差异、前端构建产物及运行配置等实际发布所需内容。
2. 优先查找 C 已形成的可用整合候选。若缺失，Z 在隔离工作区制作并验证发布组合的可行性，提出准确的组合顺序和候选坐标。属于业务代码整合或 Gitee 正式入库的事项由 C 负责；Z 不擅自修改 C 的资料库、不直接向生产分支推送。确需 C 配合时一次性列出具体冲突、输入和所需操作，优先共享已存在成果，不让 C 重做已完成的工作。
3. 若组合候选产生实质代码差异，进行受影响模块的必要回归；未变化且证据可信的专项不重跑。针对新组合至少核实身份授权、撤销机制、备份恢复、发布失败退出与回滚等真实相邻路径。不能把旧独立候选测试结果自动当成新组合已通过。
4. 对 NAS 恢复链，复用上一轮恢复证据，只核对新组合或真实环境差异引入的风险。验证重要记忆、上传文件及恢复落点契约仍有效；真实生产备份链重建和首次成功备份/恢复验证列入授权后执行清单。不得以临时测试数据通过推定生产数据已经受保护。
5. 给出明确的生产发布输入清单：唯一候选或可核实的组合方案、构建产物来源、配置变更、数据迁移依赖、服务停写要求、部署顺序、必要健康检查及成功判据。不可获取、不可复现或有未解释冲突时，不得宣称发布就绪。

验收：候选组合与既有修复关系清楚，保留必要证据，所有新增差异已验证或明确标为待处理。若不能形成唯一可发布候选，须提供可执行的 C 协作请求，不虚构最终坐标。

### M4｜生产回滚准备（A4）

目标：发布失败时能够安全恢复服务及重要数据，而不是仅依赖人工切回一个 Git 标签。

1. 核对已有 S1 发布安全成果、脚本入口及所覆盖的失败路径，禁止从零重写已验收工具。明确当前生产缺的是工具安装、可用回滚点、产物、配置还是数据恢复契约。
2. 只读检查当前生产可获取的基线资料和恢复依赖，提出实际回滚点构成：代码、构建产物、运行配置（不暴露秘密）、数据和兼容性、服务启动方式及必要证据。区分本次已在隔离中制作的回滚点与授权后才能建立的真实生产回滚点。
3. 在隔离环境以已有工具演练一次有代表性的发布失败与回滚，核对真实退出码、服务恢复、产物一致性、重要数据可读及配置兼容。仅增加因新组合产生的必要故障用例，不重复 S1 全量演练。
4. 明确回滚触发条件：候选指纹不符、关键迁移失败、身份或权限验证失败、重要数据恢复失败、服务健康异常等。回滚必须防止凭证复活或恢复旧的不安全认证配置；如果旧版本与新数据/凭证不兼容，提出安全停止及人工恢复策略，而非承诺一定能自动回滚。
5. 在授权后实际发布前必须创建并核验真实生产回滚点；不能建立或验证则不得发布。仅成功执行回滚命令不等于恢复成功。

验收：隔离回滚演练有可复现证据；生产回滚点、依赖与验证方式明确；没有新证据前保留生产回滚不足状态。

## 五、最终发布授权方案（本轮只提交，不执行）

Z 需一次性提交分步骤的授权方案，使主人不需要自行判断复杂技术细节。每一步列出必要性、对象类别、是否有停机或停写、预期影响、前置条件、成功证据、失败退出和回滚措施。推荐顺序须以实际依赖关系为准，不机械照搬表格。

| 授权事项 | 最低要求 |
|---|---|
| 安全维护窗口与生产回滚点 | 明确窗口、服务影响及恢复验证，先保护现有数据 |
| 本机免密身份处置 | 证明合法主人访问不被锁死，高权默认拒绝 |
| 凭证安全注入、轮换和副本处置 | 列明依赖与安全顺序；删除历史数据、远端包等不可逆操作单列授权 |

| 上线后安全门禁复核 | 真实生产证据与剩余风险；失败按方案停止或回滚 |

**审批原则：** 可将关联且风险边界清楚的动作合并成一次主人审批，避免反复询问。涉及不可逆操作、超出成本权限、无法安全回退等情况须单列，不允许以笼统的“同意任务”替代具体生产授权。未授权不执行。
